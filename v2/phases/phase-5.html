نسخهٔ قابل ساخت هنوز نسخهٔ قابل انتشار نیست

از بستهٔ فاز ۴، commit هدف، scriptهای واقعی، قرارداد هویت، migrationها، تست و مسائل باز را بخوان. مالک حساب/دامنه، محیط staging/production و اختیار انتشار/هزینه باید معلوم باشند. نبود دسترسی یا اجازه، اقدام وابسته را مسدود می‌کند؛ برنامه‌ریزی مستقل می‌تواند ادامه یابد. این صفحه مجوز یا گزارش انتشار سایت یا محصول تو نیست.

مثال آموزشی TaskFlow از React/Vite/TypeScript در frontend و Express/TypeScript در backend با PostgreSQL و Auth0 استفاده می‌کند. اینجا سرویس، حساب، تست یا deploy واقعی اجرا نشده است. فناوری پروژهٔ تو با قیود واقعی انتخاب می‌شود؛ نصب و راه‌اندازی مهارت‌های لازم پیش‌نیاز اجرای فرمان‌هاست.

۱. تصمیم‌های انتشار را به نقشه تبدیل کن

پیش از دست‌زدن به محیط، مقصد، نسخه، داده، هزینه، مالک و راه بازیابی را روشن کن. ورودی، محصول متصل و قیود استقرار است؛ خروجی wayfinder نقشهٔ تصمیم‌های وابسته است، نه انتشار.

قبل: «روی Render ببر، تمام است». اصلاح: «کدام commit، کدام محیط و DB، کدام حساب مجاز، چه داده‌ای و چه معیار برگشت؟» بودجهٔ نامعلوم فاز ۰ هنوز با فرض پلن رایگان حل نمی‌شود.

الان انجام بده

بستهٔ معتبر و محدودیت واقعی پروژه را در دسترس ایجنت بگذار؛ فقط اطلاعات واقعاً ناموجود را اضافه کن. در سشن ایجنت $wayfinder را همراه این متن فعال کن؛ فرمان shell نیست. ورودی تکمیلی فقط همین پیش‌نمایش را تغییر می‌دهد؛ سایت متن را ذخیره، ارسال یا اجرا نمی‌کند.

فقط اطلاعات واقعاً ناموجود را اضافه کن؛ مسیر مخزن لازم نیست. خالی‌بودن این ورودی به معنی اجازهٔ حدس نیست. تغییر این فیلد فرمان‌های دیگر را تغییر نمی‌دهد.

۲. نقشهٔ موجود را ادامه بده

در سشن تازه به نقشهٔ معتبر برگرد؛ یک تصمیم آماده بدون مانع و claim را claim و حل کن. پرسش انسانی را ایجنت به‌جای صاحب اختیار پاسخ نمی‌دهد.

پاسخ در تیکت و gist/لینک در نقشه، وابستگی و مسائل باز به‌روز شوند. حل یک تصمیم پایان برنامهٔ انتشار نیست.

۳. محیط را از روی برنامهٔ واقعی تنظیم کن

اول staging با دیتابیس جدا و دادهٔ آزمون مجاز، بعد production با اختیار مربوط. build و تست باید برای همان commit و نسخهٔ Node/lockfile ثبت شوند؛ موفقیت لوکال، تنظیم درست سرویس را اثبات نمی‌کند.

TaskFlow: مقصد پیشنهادی روشن

Render با یک Static Site، یک Node Web Service و PostgreSQL مدیریت‌شده، مسیر نمونه را در یک میزبان نگه می‌دارد. Auth0 ورود واقعی فاز ۴ را تأمین می‌کند. هزینه و قابلیت‌های پلن، منطقه و دسترسی باید بررسی شوند؛ این انتخاب آموزشی به پروژهٔ تو تحمیل نمی‌شود.

الان انجام بده

برای پروژهٔ خودت نام محیط، commit، نسخهٔ Node.js 24 LTS نمونه، تنظیم build/start، متغیرهای عمومی/محرمانه و مالک مقداردهی را در runbook ثبت کن. در اجرای مجاز، مخزن و شاخهٔ انتشار را در داشبورد Render متصل کن؛ تا آماده‌شدن انتشار مجاز، trigger خودکار را فعال نکن. تنظیمات نمونه را با scriptهای واقعاً ساخته‌شدهٔ فاز ۴ تطبیق بده.

سرور به پورت محیط PORT و host برابر 0.0.0.0 گوش می‌دهد؛ پورت لوکال یا یک عدد ثابت را تنها پورت اجرا نگذار. Health Check Path نمونه /health است: بررسی کوتاه دسترسی ضروری سرویس/DB طبق قرارداد، پاسخ امن، بدون نمایش اسرار؛ health موفق جای آزمون جریان نیست. NODE_ENV=production، CORS با origin دقیق HTTPS فرانت و Authorization header؛ CORS احراز هویت نیست.

فرانت و API باید HTTPS معتبر داشته باشند؛ دامنهٔ سفارشی فقط با اختیار مالک و DNS درست. نسخهٔ هدف و نتیجهٔ build/deploy را ثبت کن. در CI، scriptهای build/typecheck/test واقعیِ frontend/backend و تست مرورگری لازم پیش از promote اجرا شوند؛ نام script فرضی نساز. lockfile هر پوشه مبنای npm ci است. trigger انتشارِ شاخه و سیاست خودکار پس از CI را مطابق اختیار توافق‌شده تنظیم کن؛ شکست بررسی، ارتقا را متوقف کند.

منابع تنظیمات: Render Web Services، Express روی Render، rewrite مسیر SPA و PostgreSQL و اتصال داخلی.

هویت، متغیر محیط و اسرار در مقصد نهایی

Auth0 SPA و API از قرارداد فاز ۳/۴ استفاده می‌کنند: public domain/clientId/audience و callback، logout URL و Allowed Web Origins دقیقاً برابر URL واقعی فرانت هر محیط؛ مقادیر staging به production تعمیم خودکار ندارند. مقدار issuer/audience معتبر API و نگاشت User/role/team سروری نیز برای همان محیط بررسی شوند. دو حساب نمایشی بدون هویت واقعی و عضویت معتبر، آزمون امنیت نیستند.

متغیرهای VITE در bundle عمومی و هنگام build جای‌گذاری می‌شوند؛ تغییر API URL یا پیکربندی عمومی هویت نیازمند rebuild/redeploy است. DATABASE_URL، token، credential و client secret در فرانت، Git، چت یا log قرار نگیرند. مقدار را در محل امن میزبان و با دسترسی حداقلی نگه دار؛ در runbook فقط نام، محیط و مالک بنویس. تحویل دسترسی از کانال امن و با بررسی ورود فرد مسئول باشد؛ اسرار را در راهنمای عمومی نچسبان.

منابع: متغیرهای Vite و زمان build و پیکربندی رسمی Auth0 React و originها.

خروجی را بررسی کن

آیا فرانت به API همان محیط وصل است و DBها جدا هستند؟ build/start واقعاً وجود دارند؟ URL هویت، CORS و HTTPS مطابق مقصدند؟ نبود اختیار حساب/هزینه مانع اجرای وابسته است؛ مقدار محرمانه را برای اثبات تنظیمات نمایش نده.

۴. پیش از دادهٔ واقعی، بازیابی را تمرین کن

migration، backup و restore سه کار جدا هستند. قبل از تغییر production، اجرای migration روی staging با دادهٔ موجود و بازیابی در محیط جدا را بررسی کن. صرف وجود فایل backup یا نشان سبز داشبورد، شاهد بازیابی نیست.

TaskFlow: مسئول از داده حذف نشود

اشتباه: «schema عوض شد؛ دوباره seed می‌کنیم». اصلاح: دادهٔ موجود Task/User، مسئول و وضعیت باید پس از migration حفظ و FLOW-01 قابل اجرا باشد. seed آموزشی برای staging است؛ جای بازیابی دادهٔ کاربر نیست.

الان انجام بده

مالک داده، زمان/شرایط migration، backup، هدف از دست‌رفتن مجاز داده (RPO) و زمان بازیابی (RTO) را با صاحب اختیار تعیین کن. برای تمرین می‌توان RPO یک ساعت و RTO چهار ساعت پیشنهاد کرد؛ این عددها تضمین سرویس یا توافق واقعی نیستند. restore را در DB مجزای آزمایشی انجام بده و زمان و نتیجهٔ واقعی را ثبت کن؛ بدون تمرین موفق، آمادهٔ بازیابی معرفی نکن.

اجرای migration و restore متناسب با پلن

فاز ۴ باید migrationهای مرتب و script واقعی db:migrate را ساخته و آزموده باشد. در staging همان script را با DB هدفِ تأییدشده، یک‌بار توسط یک job کنترل‌شده اجرا کن و schema/version و داده را بررسی کن. Render pre-deploy command به نوع سرویس/پلن وابسته است؛ اگر در پلن منتخب وجود دارد، npm run db:migrate فقط پس از تعریف script و احراز محیط در آن قرار می‌گیرد. در غیر این صورت job مجاز جدا با همان release و DB طبق runbook لازم است؛ فرمان lifecycle همگانی و رایگان فرض نکن و migration را به هر restart سرور گره نزن.

backup/retention واقعی پلن را انتخاب و مالک/مسیر امن و کنترل دسترسی را ثبت کن. PITR در پلن‌های پشتیبانی‌شده DB تازه می‌سازد؛ قابلیت و پنجرهٔ نگهداری را از مستندات روز بررسی کن. در تمرینِ restore، snapshot/زمان هدف را انتخاب، در DB جدا بازیابی، schema و تعداد/نمونهٔ Task و ارتباط مسئول را بررسی و FLOW-01 را در محیط جدا اجرا کن. زمان آغاز/پایان، فاصلهٔ دادهٔ ازدست‌رفته، نتیجه و مسئول cutover را ثبت کن. فقط پس از اعتبارسنجی و اختیار، اتصال سرویس به DB بازیابی‌شده عوض می‌شود؛ production را محل تمرین restore نکن.

منابع: pre-deploy و قیود پلن و backup و PITR در Render.

خروجی را بررسی کن

آیا دادهٔ قدیمی بعد از migration سالم و restore واقعاً آزموده شده؟ RPO/RTO، مالک و زمان رسیدگی روشن‌اند؟ اگر backup ضروری قابل بازیابی نیست، انتشار آماده نیست؛ این مانع را با عبارت «بعداً بررسی» پنهان نکن.

۵. بازگشت برنامه را از بازیابی داده جدا کن

برگشت frontend/backend، دادهٔ نوشته‌شده یا schema را خودکار برنمی‌گرداند. نسخهٔ قبلی باید با schema و دادهٔ جدید سازگار باشد؛ ترتیب برگشت سرویس‌ها و آزمون بعدش بخشی از برنامهٔ انتشار است.

TaskFlow: شمارنده با نسخهٔ قدیمی هم درست بماند

اگر release تازه INT-02 را خراب کرد، نسخهٔ سالم frontend/backend را با schema سازگار بازگردان و FLOW-01 و شمارنده را دوباره بسنج. اگر migration داده را خراب کرده، برگشت کد کافی نیست؛ نوشتن تازه را مهار و روند بازیابی داده با مسئول حادثه را فعال کن.

الان انجام بده

برای هر release، commit/artifact سالم قبلی، schemaهای سازگار، صاحب تصمیم برگشت و معیار توقف را در runbook ثبت کن. یک rehearsal در staging اجرا کن: ارتقا، rollback برنامه، بررسی هویت/داده و جریان. اگر داده در خطر است، پیش از rollback عجولانه وضعیت نوشتن و بازیابی را با صاحب اختیار روشن کن.

طرح برگشت قابل اجرا

migration افزایشی و expand/contract کمک می‌کند هر دو نسخه مدتی با schema کار کنند؛ حذف/تغییر مخرب را تا خروج نسخهٔ قبلی و برنامهٔ بازیابی عقب بینداز. down migration مخرب راه‌حل پیش‌فرض نیست. در Render از rollback سرویس به deploy سالم قبلی استفاده می‌شود؛ تنظیمات محیط، گروه‌های مشترک و redirect/header را جدا بررسی کن و فرض نکن همهٔ تنظیمات خودکار عقب می‌روند. frontend/backend و API URL/Auth0/CORS باید پس از برگشت هماهنگ بمانند. سپس health، ورود واقعی، ذخیره، ماندگاری و AC-01 دوباره بررسی و شاهد تازه ثبت شوند.

معیار پیشنهادی تمرین: شکست ذخیره/انجام یا مغایرت شمارنده در smoke، یا نقض دسترسی، جلوی promote را می‌گیرد؛ در production مسئول حادثه با توجه به خطر داده، برگشت برنامه یا توقف نوشتن/بازیابی را انتخاب می‌کند. این معیار را در پروژهٔ واقعی با مالک و آستانهٔ پذیرفته‌شده نهایی کن. منبع: رفتار و محدودیت rollback در Render.

خروجی را بررسی کن

آیا نسخهٔ قبلی با DB فعلی کار می‌کند و مسیر بازگشت تمرین شده؟ آزمون rollback برنامه را شاهد restore دیتابیس ننام. اگر schema ناسازگار است، برنامه را پیش از انتشار اصلاح کن.

۶. برنامهٔ انتشار را به spec تبدیل کن

پس از رفع تصمیم‌های مانع، توافق محیط/داده/بازگشت/عملیات را در spec ثبت کن. این فرمان اجرا نمی‌کند و مصاحبهٔ برنامه‌ریزی تازه نیست.

TaskFlow

spec شامل build/deploy همان نسخه، migration/restore/rollback، smoke واقعی FLOW-01 و تحویل به مسئول است؛ گزارش و پرداختِ خارج محدوده وارد release نمی‌شوند.

الان انجام بده

از تصمیم‌های معتبر و CP-4 استفاده کن و مرزهای ارزیابی پیشنهادی را طبق خود مهارت بررسی کن. در سشن ایجنت $to-spec را همراه این متن فعال کن؛ فرمان shell نیست. ورودی تکمیلی فقط همین پیش‌نمایش را تغییر می‌دهد؛ سایت متن را ذخیره، ارسال یا اجرا نمی‌کند.

فقط اطلاعات واقعاً ناموجود را اضافه کن؛ مسیر مخزن لازم نیست. خالی‌بودن این ورودی به معنی اجازهٔ حدس نیست. تغییر این فیلد فرمان‌های دیگر را تغییر نمی‌دهد.

۷. خروجی‌های انتشار را تیکت‌بندی کن
