۱. ابزار تصمیم‌گیری را آماده کن

در پوشهٔ محصولی که در فاز ۲ ساخته‌ای، سشن ایجنت لوکال را باز کن. بسته، تصمیم‌ها، روش اجرای فرانت، شواهد و مسائل باز باید از فهرست ورود قابل کشف باشند. نصب مهارت، اجرای موفق محصول یا اختیار ساخت ایجاد نمی‌کند.

TaskFlow: از فرانت به طراحی

فرانت React/TypeScript در frontend/ جریان FLOW-01 را با mock نشان می‌دهد؛ نقش‌ها شبیه‌سازی‌اند. قرارداد فعلیِ gateway را ورودی طراحی بدان، نه مدل قطعی API. اگر فرانت واقعاً اجرا نشده، همان را در بسته ثبت کن؛ متن این مثال شاهد اجرا نیست.

الان انجام بده

با Node.js 24 LTS، Git، شبکه و Codex نصب‌شدهٔ فاز ۲، یکی از دو روش نصب upstream را انتخاب کن. در ترمینال، روش افزونهٔ Codex:

روش جایگزین: فایل‌های قابل ویرایش محلی

npx skills@latest add mattpocock/skills -a codex

مهارت‌های setup-matt-pocock-skills، wayfinder، grill-with-docs، to-spec، to-tickets، implement-spec و implement باید قابل کشف باشند. در سشن پروژه $setup-matt-pocock-skills را یک بار فعال کن؛ با یافته‌های مخزن، tracker و چیدمان اسناد را بررسی و طبق مراحل خود مهارت تأیید کن. پیشنهاد نمونه: tracker محلی Markdown در .scratch/<feature>/، واژه‌نامهٔ ریشه و docs/adr/. این سایت پیکربندی پروژهٔ تو را تغییر نمی‌دهد.

اگر مهارت دیده نمی‌شود، مسیر نصب/فهرست مهارت‌های ایجنت را بررسی و در صورت نیاز سشن را دوباره باز کن. در این صفحه نام مهارت یعنی فعال‌کردن آن داخل ایجنت؛ نوشتن $wayfinder یا نمایش /wayfinder در برخی میزبان‌ها فرمان shell نیست. پرامپت کنار هر اقدام را همراه مهارت انتخاب‌شده بفرست.

منبع نصب و رفتار جاری: مخزن رسمی Matt Pocock. نسخهٔ نصب‌شده و SKILL.md آن را بخوان؛ نام و روش فراخوانی میزبان ممکن است تغییر کند. مهارت‌های بالا از همین upstream هستند؛ frontend-design از Anthropic و ui-ux-pro-max از nextlevelbuilder است و به Matt نسبت داده نمی‌شوند.

۴. از رفتار به مدل و قرارداد برس

برای هر عملیات بپرس چه کسی، روی کدام داده، با چه پیش‌شرطی و چه نتیجه‌ای کار می‌کند. نام فیلدهای mock فقط پیشنهاد است. تصمیم‌های دامنه را در واژه‌نامه و ADR مرتبط نگه دار؛ تغییر معنای رفتار باید به مرجع محصول و سناریوهای متأثر برگردد.

TaskFlow: مسئول، یک نام نمایشی نیست

قبل: کار فقط assigneeName دارد و فرانت نقش را می‌فرستد. اشکال: هم‌نامی و جعل نقش ممکن است. اصلاح پیشنهادی: User با شناسهٔ داخلی، عضویت تیم و نقشِ ثبت‌شده در سرور؛ Task با شناسه، teamId، عنوان، assigneeId، وضعیت open/done، نسخه و زمان‌ها. نام برای نمایش است؛ نقش و تیم از درخواست کاربر پذیرفته نمی‌شوند.

قرارداد نمونهٔ FLOW-01؛ جزئیات لازم برای طراحی

این قرارداد آموزشی با AC-01 تا AC-05 فاز ۱ سازگار است؛ برای تمرین صریحاً آن‌ها را مبنا انتخاب کن. در محصول واقعی وضعیت تصویب رفتار و اختیار جدا ثبت می‌شوند. SCREEN-01 فهرست و SCREEN-02 فرم‌اند؛ INT-01 ثبت و INT-02 تغییر وضعیت. پرداخت، گزارش تحلیلی و اپ بومی همچنان خارج محدوده‌اند.

عملیاتقرارداد قابل بررسی
GET /api/meهویت معتبر به User محلی نگاشت؛ id، role و teamId معتبر سرور برای رابط برمی‌گردد. حساب معتبرِ بدون عضویت فعال 403 می‌گیرد.
GET /api/assigneesفقط سرپرست؛ همکاران فعال همان تیم با id و نام برای انتخاب مسئول. مسئول عضو تیم دیگر قابل انتخاب نیست.
GET /api/tasksسرپرست همهٔ کارهای تیم خودش؛ همکار فقط کارهای خودش. پاسخ items و openCount از یک دامنه و تصویر سازگار داده؛ فهرست خالی 200 با [] و صفر است (AC-04).
POST /api/tasks — INT-01فقط سرپرست؛ title.trim غیرخالی و assigneeId عضو فعال همان تیم اجباری؛ clientRequestId یکتا برای هر قصد ثبت، با کلید یکتای teamId/actorId/clientRequestId برای تکرار امن همان درخواست؛ 201 با Task ذخیره‌شده و وضعیت open. عنوان خالی یا مسئول نامعتبر 422 با خطای فیلد و بدون رکورد (AC-02).
PATCH /api/tasks/:id/status — INT-02در جریان پایه فقط همکارِ مسئول، open را به done می‌برد؛ بدنه status و expectedVersion دارد. موفقیت 200 با Task و نسخهٔ جدید؛ تکرار با نسخهٔ قدیمی 409 و دریافت دوباره. ویرایش عمومی و بازگشایی تصمیم این جریان نیست.

همهٔ عملیات به هویت معتبر نیاز دارند؛ نبود/انقضای token = 401، نقش نامجاز = 403، کار خارج از دید یا ناموجود = 404، تعارض نسخه = 409، اعتبارسنجی = 422، شکست غیرمنتظره = 500 با پیام عمومی و requestId. قالب خطا: code، message، fieldErrors اختیاری و requestId؛ جزئیات داخلی و token در پیام/log نروند. تیم و مسئول از دادهٔ معتبر سرور بررسی می‌شوند؛ فیلتر UI کافی نیست.

Task به User و Team با رابطهٔ معتبر وصل است؛ تغییر وضعیت، افزایش نسخه و ذخیره در یک عملیات اتمی انجام می‌شوند. INT-01 و INT-02 خودکار retry نمی‌شوند؛ پس از پاسخ مبهم شبکه، ثبت با همان clientRequestId و همان بدنه دوباره درخواست می‌شود و همان رکورد برمی‌گردد؛ استفادهٔ همان کلید با بدنهٔ متفاوت 409 است. برای تغییر وضعیت ابتدا رکورد دوباره دریافت و نسخه بررسی می‌شود. موفقیت فقط پس از تأیید سرور؛ پس از هر موفقیت فهرست و شمارنده از منبع مشترک دوباره دریافت می‌شوند (AC-01). شکست ذخیره ورودی فرم را حفظ و پیام/تلاش دوباره نشان می‌دهد (AC-03). OPEN-01 شمارندهٔ کهنه فعلاً خطای فرضی است؛ TEST-01 هنوز Not Tested.

تصمیم هویت نمونه؛ دو کاربر نمایشی احراز هویت نیستند

برای نمونه، انتخاب آموزشیِ روشن Auth0 با ورود میزبانی‌شده و OIDC Authorization Code + PKCE است: مدیریت ورود را به ارائه‌دهنده می‌سپاریم تا رمز و جریان ورود اختصاصی نسازیم. هزینه، دسترسی شبکه و حساب ارائه‌دهنده وابستگی واقعی‌اند؛ پذیرش این وابستگی توسط صاحب اختیار باید قبل از اجرای جریان فاز ۴ ثبت شود. گزینهٔ جایگزینِ هویت سازمانی موجود می‌تواند مناسب‌تر باشد؛ تغییر آن تصمیمی مستدل و قرارداد تازه می‌خواهد.

SPA ثبت‌شده با Client ID عمومی و audience مخصوص API، access token را به‌صورت Bearer به Express می‌دهد؛ secret در فرانت وجود ندارد و ID token جای access token API نیست. API با کتابخانهٔ معتبر امضا و الگوریتم مجاز، issuer، audience و انقضا را بررسی می‌کند؛ سپس زوج issuer/sub را به User فعالِ از پیش ثبت‌شده نگاشت می‌کند. نقش و teamId فقط از دیتابیس می‌آیند؛ ورود موفق نقش سرپرست ایجاد نمی‌کند. token نامعتبر 401 و هویت ناشناخته/بدون عضویت 403 دارد. دو حساب آزمون باید در ارائه‌دهنده واقعی و عضویت سروری جدا داشته باشند؛ تغییر نقش mock، آزمون امنیت نیست.

در فاز ۴ مالک مجاز، یک برنامهٔ SPA و API در حساب ارائه‌دهنده آماده می‌کند؛ issuer، audience و دو نگاشت حساب ثبت می‌شوند. callback، logout URL و allowed web origin باید دقیقاً با URL واقعی فرانت لوکال و staging مطابق باشند؛ پورت چاپ‌شدهٔ Vite را بخوان. در فاز ۵ آدرس HTTPS فرانت Render نیز صریح تنظیم می‌شود؛ wildcard یا localhost تولید نگذار. session و token توسط SDK نگهداری شوند؛ token را در کد، چت یا log ثبت نکن. انقضا/خروج باید رابط را از دادهٔ محافظت‌شده خارج کند؛ فاز ۴ آن را واقعاً می‌سنجد.

منابع: معماری رسمی SPA و API، اعتبارسنجی access token و SDK رسمی React و تنظیم originها. این صفحه حسابی ایجاد و SDKای نصب نمی‌کند.

خروجی را بررسی کن

آیا شخص غیرمجاز با درخواست مستقیم هم رد می‌شود؟ آیا هر خطا به رفتار روشن فرانت وصل است؟ DEC-03/AC-06 ویرایش کار همکار همچنان باز است؛ آن را با مجوز تغییر وضعیت کار خود خلط نکن. اگر هویت، مالک حساب یا سیاست دسترسی معلوم نیست، اتصال وابسته مسدود است؛ این کمبود را به فاز انتشار منتقل نکن.

۵. فناوری را با مقصد واقعی تطبیق بده

همین حالا انتخاب سرور، ذخیره‌سازی و محدودیت میزبانی را روشن کن تا قرارداد قابل ساخت باشد. فاز ۳ محل ثبت تصمیم است؛ پوشه و اسکریپت و migration واقعی در فاز ۴ ساخته می‌شوند.

TaskFlow: پیشنهاد DEC-02

Express + TypeScript + PostgreSQL با همان Node.js 24 LTS: زبان اپلیکیشن مشترک، قرارداد HTTP صریح و رابطهٔ Task/User پایدار. Render برای static frontend، Node web service و PostgreSQL مدیریت‌شده پیشنهاد آموزشی است تا مسیر استقرار مشخص بماند. راه تابعی هم ممکن است، اما محدودیت اتصال دیتابیس و اجرا باید دوباره بررسی شود؛ انتخاب از روی مد نیست.

الان انجام بده

در DEC-02 پروژهٔ خودت گزینهٔ منتخب/ردشده، دلیل، شواهد محدودیت‌ها، هزینهٔ نامعلوم و صاحب تصمیم را ثبت کن. برای نمونه backend/ کنار frontend/ در همان مخزن با package.json و lockfile مستقل برنامه‌ریزی می‌شود؛ workspace تازه لازم نیست. بودجهٔ TaskFlow هنوز نامعلوم است؛ هزینه یا پلن رایگان را تضمین نکن و provisioning را مجاز ندان.

قیود پیاده‌سازی و استقرار که در قرارداد می‌مانند

Express یک فرایند Node پایدار می‌خواهد؛ سرور باید PORT محیط و host مناسب میزبان را بپذیرد. PostgreSQL با ذخیرهٔ پایدار، migration نسخه‌دار و طرح بازیابی؛ فایل موقت سرویس محل داده نیست. frontend خروجی build دارد و API عمومی HTTPS؛ backend و DB ترجیحاً هم‌منطقه با اتصال داخلی. DATABASE_URL و مقادیر محرمانه فقط سرور؛ متغیر VITE عمومی است. CORS باید origin دقیق فرانت و Authorization را بپذیرد؛ CORS احراز هویت نیست. تنظیم Auth0 از بخش هویت با URL واقعی میزبان هماهنگ می‌شود.

برای فاز ۴ ساخت اسکریپت‌های dev/build/start/test/typecheck/db:migrate و تعریف دقیق عملکردشان را برنامه‌ریزی کن؛ این نام‌ها خودکار با Express ایجاد نمی‌شوند. قبل از ساخت آن‌ها فرمان npm run فرضی اجرا نکن. سقف حجم و زمان پاسخ را از نیاز واقعی بگیر؛ عدد آموزشی تعهد کارایی نیست. منبع محدودیت‌ها: نصب رسمی Express، Web Service در Render و اتصال PostgreSQL در Render.
