# 01: اصلاح مسیر ساخت پروتوتایپ و تحویل فاز دو

**What to build:** توسعه‌دهنده از آموزش، کارگاه و مرکز پروتوتایپ فاز دو، مسیر ساخت با سایت‌های vibe coding را دنبال کند و بستهٔ مرجع محصول، سورس و شواهد مناسب ورود به توسعه را تحویل بگیرد. این تیکت اصلاح وابستهٔ فاز دو در spec تأییدشدهٔ «تکمیل راهنمای توسعه تا تحویل: فازهای سه تا هشت» است؛ محصول کار خود سایت راهنماست.

**Blocked by:** None (can start immediately).

**Status:** ready-for-agent

- [ ] مسیر فعال ساخت و فرمان‌های مرتبط فقط سایت‌های vibe coding را پوشش دهند؛ ابزار صرفاً طراحی UI/UX مانند Stitch و ارجاع‌های فعال آن از این مسیر کنار بروند. مثال‌های Replit و Base44 بدون ادعای تأییدنشده دربارهٔ قابلیت فعلی آن‌ها معرفی شوند؛ راهنمای تخصصی تازه برای Base44 الزام این تیکت نیست.
- [ ] بررسی پیشینی امکان خروج سورس و توسعهٔ مستقل، شرط انتخاب یا پذیرش ابزار نشود؛ وجود سورس و شواهد لازم برای تحویل آماده به توسعه همچنان شرط باشد.
- [ ] آموزش و فرمان‌ها قرارداد پروتوتایپ فرانت بدون بک‌اند واقعی را حفظ کنند و روش بررسی خروجی واقعی ابزار برای بک‌اند، احراز هویت واقعی و وابستگی اختصاصی ناخواسته را توضیح دهند. عدم انطباق به اصلاح نمونه برگردد؛ بک‌اند تولیدشده خودکار معماری نهایی محسوب نشود.
- [ ] تعریف رفتار MVP مرجع صحت باقی بماند؛ فناوری، کتابخانه، ساختار و کیفیت مشخصی برای سورس فرض نشود. حفظ سورس قابل‌قبول ترجیح داشته باشد و اصلاح یا بازسازی با دلیل و هزینه مقایسه شود.
- [ ] مثال آموزشی TaskFlow، تحویل سورس و شواهد، شبیه‌سازی صریح و حالت شکست را نشان دهد؛ برای کمبودها وضعیت و اقدام بعدی معلوم باشد. مثال آموزشی شاهد اجرای واقعی معرفی نشود.
- [ ] آموزش، کارگاه، مسیر ابزارها و فرمان‌های متأثر با یکدیگر سازگار باشند؛ پیش‌نمایش و کپی، لینک‌ها و fragmentها، صفحه‌کلید و نمایش در عرض‌های دسکتاپ، تبلت و موبایل بررسی شوند. ارزیابی‌های تاریخی به‌عنوان شاهد نسخهٔ تازه بازنویسی نشوند.
- [ ] پس از بررسی‌های متناسب و code review، در همان چت راهنمای ارزیابی feature-by-feature با ورودی، اقدام، انتظار، checkpoint، شاهد واقعی preflight و نخستین اقدام مشخص کاربر آماده شود. موارد انجام‌نشده صریح بمانند و پذیرش انسانی تا گزارش مشاهدات کاربر pending باشد.
