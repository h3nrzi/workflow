01

نسخهٔ مبنا

سورس پروتوتایپ، Commit یا Snapshot اولیه و مراحل اجرای آن قابل دسترسی باشند. هیچ چیزی فقط در محیط سازنده باقی نمانده باشد.

02

قرارداد محصول

Product Experience Package، Prototype Handoff، وضعیت ACها و تفاوت‌های نمونه با طراحی مرجع معلوم باشند.

03

مقصد و اختیار

Monorepo موجود یا ساختار مقصد تعیین شده و اجازهٔ مهاجرت، هزینه، دسترسی‌ها و تغییر کد از هم جدا بررسی شوند.

اگر Monorepo هنوز وجود نداره، Agent نباید خودسرانه ابزار Build یا ساختار پوشه‌ها رو انتخاب کنه. انتخاب زیرساخت خودش یک تصمیمِ نیازمند بررسی و تأیید است؛ ممکنه یک Ticket مستقل یا آزمایش فنی کوتاه لازم داشته باشه.

توقف درست

نبود سورس، نداشتن مجوز، عدم دسترسی به مقصد یا تعارض جدی لایسنس و امنیت، مانع شروع پیاده‌سازی است. در این حالت می‌توان گزارش ابهام و اقدامات مقدماتی تهیه کرد؛ نباید نتیجهٔ مهاجرت را جعل کرد.

گام صفر / قبل از Skill

Local Readiness؛ چیزی را که نداریم حدس نزنیم

پروتوتایپ را در یک مسیر کنترل‌شده و جدا از تغییرات مقصد بررسی کن. اجرای `npm install` یا اسکریپت‌های ناشناس ممکن است کد دلخواه اجرا کند؛ قبل از آن `package.json`، دستورات نصب، lockfile، وابستگی‌ها و فایل‌های حساس را مرور کن. هرجا امکان‌پذیره محیط ایزوله و دسترسی حداقلی استفاده کن.

Skill اصلی / Align

grill-with-docs واقعاً چه خروجی دارد؟

این Skill یک جلسهٔ پرسش‌گری وابسته به کدبیس موجود اجرا می‌کنه: سؤال‌ها رو یکی‌یکی می‌پرسه و هرجا کد جواب می‌ده خودش به فایل مراجعه می‌کنه. اصطلاحات حل‌شده در GLOSSARY.md ذخیره می‌شن؛ تصمیم‌های واجد شرایط ADR در docs/adr/ می‌گیرن. اغلب تصمیم‌های روزمره ممکنه فقط در خود مکالمه باقی بمونن.

سه سؤال نمونهٔ مرتبط با مهاجرتنه خروجی واقعی یک سشن
۱

کدام قابلیت پروتوتایپ باید بدون تغییر رفتار منتقل شود و کدام رفتار صرفاً دموست؟

۲

وابستگی‌های خاص محیط سازنده یا پیکربندی مقصد کدام‌اند؟ ابتدا Agent از کد پاسخ دهد.

۳

انتقال یک Component به پکیج مشترک، تصمیم ضروری است یا صرفاً بازآرایی خوشایند؟

نشانه‌های اجرای درست Skill

  • Skills وابستهٔ grilling و domain-modeling نصب/قابل بارگیری‌اند.
  • هر بار یک سؤال با توصیهٔ قابل بحث می‌آید؛ سؤال‌های قابل پاسخ از کد به انسان واگذار نمی‌شوند.
  • تعاریف اصطلاحات واقعاً در GLOSSARY.md ثبت می‌شوند؛ این فایل نباید به Spec تبدیل شود.
  • ADR فقط برای تصمیم دشوارِ برگشت، خلاف انتظار و دارای Trade-off ساخته می‌شود؛ صفر ADR هم طبیعی است.
  • جلسه پس از توافق پایان می‌یابد و همان Context برای to-spec حفظ می‌شود، یا نتیجه به‌شکلی صادقانه Handoff می‌گردد.

منابع راهنمای این رفتار، مستند اصلی Grill و تعریف Skill هستند.

برای مهاجرت چندسشنی

To Spec و To Tickets چه زمانی مفیدند؟

02

to-spec

توافق‌های Grill رو در قالب Spec ثبت می‌کنه: هدف مهاجرت، In/Out Scope، تصمیم‌های قابل ردگیری، Test Seams و معیارهای Done. نباید نیاز یا تصمیم جدید اختراع کنه.

Gate: Spec را توسعه‌دهنده با تصمیم‌های واقعی تطبیق داده؟
03

to-tickets

Spec رو به Ticketهایی با Dependency و نتیجهٔ مستقل می‌شکنه؛ ترجیح با برش‌های عمودیِ قابل Demonstrate است، نه تقسیم کورِ «اول همهٔ configها، بعد همهٔ UIها».

Gate: هر Ticket یک رفتار یا یک برش قابل آزمون دارد؟

برای /to-spec و /to-tickets ابتدا /setup-matt-pocock-skills رو در ریپازیتوری اجرا کن تا Issue Tracker و محل اسناد تنظیم بشن. در حالت GitHub یا Tracker دیگر، وجود دسترسی/ابزار لازم باید تأیید بشه؛ Local Markdown هم یک گزینه است. این دستورها رو در محیط Local و با آگاهی از فایل‌هایی که می‌نویسن اجرا کن.

نکتهٔ عملی

اگر مشکل از Refactor وسیع با اثر روی همهٔ مصرف‌کننده‌هاست، ممکنه Ticketهای سادهٔ عمودی مناسب نباشن. در این شرایط از مدل Expand → Migrate → Contract یا برش‌بندی مشابه با اجرای Test/CI بین مراحل استفاده کن.

تغییر واقعی / Diff و Test

Implement بدون شکستن رفتار مرجع

/implement باید یک Ticket یا تغییر محدود رو اجرا کنه؛ نه اینکه سرِ پیاده‌سازی دربارهٔ هدف محصول تصمیم تازه بگیره. قبل از آغاز، Branch مناسب و محدودهٔ مجاز تغییرات روشن باشه؛ Skill می‌تونه روی Branch جاری Commit ایجاد کنه.

01

Preserve

سناریوی اصلی فاز دو و Baseline را نگه دار. اگر دادهٔ نمایشی قرار است حفظ شود، انتقال نباید ناخواسته Backend واقعی بسازد.

02

Adapt

فقط آنچه برای سازگاری با Monorepo لازم است تغییر کند: مسیرها، Imports، Build Scripts یا وابستگی خاص ابزار سازنده.

03

Verify

Typecheck/Build/Test و مسیرهای ضروری را با گزارش واقعی اجرا و اختلاف‌ها را ثبت کن.

04

Review

Diff نسبت به Spec/AC و قراردادهای ریپازیتوری بررسی شود. یافته‌های Review خودکار به معنی اصلاح یا پذیرش خودکار نیست.

برای هر Ticket، یک سشن متمرکز مناسب‌تر از درخواست «همهٔ مهاجرت رو هم‌زمان اجرا کن» است. بعد از Commit، وضعیت Ticket و Acceptance Criteria را انسانی بازبینی کن؛ خود Skill الزاماً Ticket را نمی‌بندد.

شرط خروج / تصمیم انسانی

Migration Acceptance Gate

پایان این فاز «پروژه اجرا شد» نیست. باید رفتار محصول، قرارداد Monorepo و سطح واقعی آزمون روشن باشند. معیارهای اصلی:

Runtime

اپ در محیط مقصد با دستورهای ثبت‌شده اجرا می‌شود؛ نه فقط در محیط سازنده.

Behavior

سناریوهای حیاتی فاز دو در مقصد بررسی شده‌اند و اختلاف‌ها معلوم‌اند.

Repository

وابستگی‌ها، قاعدهٔ پکیج‌ها، Build/Typecheck/Test و Diff وضعیت روشن دارند.

Evidence

موارد Not Tested و Blocked، بدهی فنی، محدودیت سرویس و مجوزها پنهان نشده‌اند.

کارگاه / اجرای واقعی
