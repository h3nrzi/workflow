هدف و مرز فاز

در فاز ۳ سورس پروتوتایپ به محیط مناسب توسعه منتقل شده؛ اما مهاجرت موفق معادل صحت رفتار محصول نیست. در فاز ۴، پرامپت محصول‌محور واقعی Replit، Product Experience Package، Prototype Handoff و Migration Handoff را با سورس فعلی مقایسه می‌کنیم، Flowها را به سناریوهای قابل آزمون تبدیل می‌کنیم و نقص‌های در دامنه را با شواهد واقعی اصلاح می‌کنیم.

مرز: هدف، Verified Frontend Baseline است؛ این فاز به‌تنهایی مجوز ایجاد Backend/Auth واقعی، تغییر دامنه محصول یا انتشار Production نیست.

Entry Gate — پیش‌نیاز و ایمنی

  1. Revision سورس فعلی، Handoff فاز ۳ و امکان بازگشت به مبنا مشخص باشند.
  2. Product Prompt واقعی و شناسه‌های FLOW / SCREEN / INT / AC و نسخه منابع در دسترس یا کمبودشان ثبت شده باشد.
  3. تست در محیط ایزوله با دادهٔ غیرحساس و پس از بررسی اسکریپت‌ها و وابستگی‌ها انجام شود.
  4. اجازه اجرای تست، تغییر کد، اتصال سرویس و هزینه از هم تفکیک شود.

در غیاب شرط حیاتی، وضعیت Blocked / On Hold است؛ عدم اجرا «Passed» نیست.

Baseline و Flow Inventory

Local Coding Agent ابتدا ساختار کد، روش Run/Test و Flowهای قابل مشاهده را با ذکر Commit بررسی می‌کند. هر Flow دارای منبع انتظار، AC، اولویت، وضعیت Mock/Real و وضعیت مشاهده است. Flow فاقد انتظار تأییدشده باید Needs Decision بماند.

۱. Grill with Docs

با پرامپت محصول‌محور و شواهد کد، ابهام‌های Flow، مرز Mock و رفتار مورد انتظار را با تصمیم‌گیرنده روشن کنید. سؤال‌ها و تصمیم‌ها منبع‌دار باشند.

۲. To Spec

Flowهای در دامنه را به E2E Specification تبدیل کنید: Preconditions، Fixtures، گام‌های کاربر، Assertions قابل مشاهده، Cleanup و شناسه‌های FLOW/AC/E2E. هر حالت کم‌ارزش لازم نیست E2E شود؛ تست سطح پایین‌تر را متناسب با ریسک انتخاب کنید.

۳. To Tickets

کار را به Ticketهای کوچک مبتنی بر Flow، با Acceptance Criteria، فرمان Verification، ریسک و وابستگی تقسیم کنید.

۴. To Implement

روی همان سورس مهاجرت‌داده‌شده تست را اجرا کنید؛ شکست را دسته‌بندی، نقص واقعی را با حداقل تغییر Fix، سپس تست هدف و Regression را دوباره اجرا و نتیجه را ثبت کنید. تست را صرفاً برای سبزشدن ضعیف نکنید.

Traceability و گزارش اجرای واقعی

شناسه Flowمنبع و ACE2Eمرزنتیجهشاهد
FLOW-??Unknown / AC-??E2E-??Mock / Real / UnknownNot Tested—

وضعیت اجرای سناریو: Passed / Failed / Blocked / Not Tested. Flaky برچسب مکمل است. هر Passed باید با Commit، دستور اجرا، محیط و Artifact قابل پیگیری باشد.

مثال آموزشی TaskFlow

فرضی، نه تست اجراشده: فرض کنیم FLOW-01 ساخت Task و AC-01 نمایش Task در فهرست باشد. پس از تأیید منبع انتظار، سناریو E2E فرم را تکمیل، ثبت و نمایش نتیجه را بررسی می‌کند. اگر دکمه کار نکند ابتدا Trace جمع می‌شود و سپس مشکل در دامنه رفع و Regression اجرا می‌شود. اگر نگهداری Task پس از Refresh نیازمند Backend واقعی باشد، بدون مجوز توسعه داده نمی‌شود و به Full-stack Backlog می‌رود.

Verification Gate و Handoff

  • تمام Flowهای در دامنه به انتظارات، تست و نتیجه یا دلیل Blocked نگاشت شده‌اند.
  • تست‌های ضروری روی سورس موجود اجرا و شواهد واقعی ثبت شده‌اند.
  • نقص‌های بحرانی رفع، Regression اجرا و Flaky/Fail/Blocked شفاف گزارش شده‌اند.
  • وابستگی‌های Full-stack از Verified Frontend Baseline تفکیک شده‌اند.
  • صاحب اختیار وضعیت Ready / Conditional / Blocked و گام مجاز بعدی را ثبت کرده است.

Handoff شامل Baseline، Flow Matrix، E2E Report، Fix Log، ریسک‌ها، Full-stack Backlog و تصمیم Gate است. عبور، مجوز خودکار انتشار یا توسعه Backend نیست.

کارگاه اجرایی و پرامپت‌ها

راهنمای کارگاه شامل فرم ورودی واقعی پروژه، پرامپت مشاور برای آماده‌سازی Grill، قرارداد Spec/Tickets، پرامپت Implement و قالب ثبت گزارش E2E است. پرامپت‌ها صرفاً ابزارند و جایگزین مشاهده واقعی کد نمی‌شوند.
