WHY / پس از مهاجرت

کد مهاجرت کرده؛ آیا رفتار محصول درست است؟

فاز ۳ زیرساخت توسعه را آماده می‌کند، اما حفظ و انتقال سورس لزوماً به معنای مطابقت رفتار محصول با درخواست اولیه نیست. فاز ۴ Product Prompt واقعیِ داده‌شده به Replit و Handoffهای طراحی و پروتوتایپ را کنار سورس فعلی Monorepo می‌گذارد؛ شکاف‌ها را با تست E2E قابل تکرار آشکار می‌کند و فقط نقص‌های مصوب را اصلاح می‌کند.

INPUT · EXPECTEDآنچه باید می‌ساختیمProduct Prompt + Product Experience Package + Prototype Handoff و تصمیم‌های تأییدشده
INPUT · ACTUALآنچه واقعاً داریمCommit سورس پس از مهاجرت، رفتار Browser، پیکربندی Run و گزارش تست
خروجی: Verified Frontend Baseline به‌همراه E2E Suite، Fix Log و Handoff. این عبارت به معنی Backend کامل، امنیت تضمین‌شده یا Production Ready نیست.
ENTRY GATE / قبل از اجرای کد

ورودی، اختیار و محیط امن

01

منبع انتظار

پرامپت واقعی Replit، FLOW/SCREEN/INT/AC و نسخهٔ اسناد و تصمیم‌های مشتری.

02

Source Baseline

Commit مقصد، روش Run/Test و نقطهٔ برگشت. تغییرات کاربر دست‌نخورده می‌مانند.

03

اجازه و ایمنی

محیط ایزوله، دادهٔ ساختگی، حساب آزمایشی و مجوز اجرای تست و اصلاح کد.

قبل از نصب یا اجرای دستورهای نامعلوم، اسکریپت‌ها و وابستگی‌ها را بررسی کن. تست روی سرویس واقعی، دادهٔ مشتری یا Production بدون مجوز صریح ممنوع است. اگر ورودی حیاتی نداریم، Blocked / On Hold ثبت می‌کنیم، نه Passed.

BASELINE / INVENTORY

هر Flow یک شناسه و یک مسیر ردیابی

Agent ابتدا سورس فعلی و تنظیمات واقعی پروژه را مشاهده می‌کند؛ سپس Flowها را از منابع انتظار استخراج و با UI فعلی تطبیق می‌دهد. شناسه‌های FLOW-xx، SCREEN-xx، INT-xx و AC-xx باید حفظ شوند. رفتار صرفاً دیده‌شده در کد، تا پیش از تأیید، Observed / Needs Decision است.

معیار خروج: هیچ Flow در دامنه نباید بدون منبع انتظار، وضعیت فعلی و مالک ابهام در فهرست باقی بماند.

01

Grill with Docs

با گزارش Local Agent و Product Prompt درباره رفتارهای متناقض، مسیرهای خطا، Mock/Real و اولویت‌ها سؤال کن. خروجی: Decision Log و دامنه تأییدشده.

02

To Spec

Flowها را به سناریوهای دارای Preconditions، Actions، Observable Assertions، Fixture و Cleanup تبدیل کن. خروجی: E2E Spec.

03

To Tickets

کارهای چندسشنی را به برش‌های کوچک مبتنی بر Flow با AC و Verification تقسیم کن. برای کار کوچک و تک‌مرحله‌ای سربار اضافه نساز.

04

To Implement

تست را روی سورس فعلی اجرا، شکست را طبقه‌بندی، نقص واقعی را Fix و Regression را تکرار کن. خروجی: Diff + Result + Evidence.

این چهار Skill همان ابزارهای آشنای فاز ۳ هستند اما هدفشان اینجا اثبات رفتار محصول است، نه مهاجرت Monorepo.

E2E DESIGN / پوشش معنادار

تمام Flowها ردیابی شوند، نه اینکه همه چیز E2E شود

برای هر Flow در دامنه، حداقل سناریوی اصلی و خطاهای حیاتی متناسب با ریسک را مشخص کن. وضعیت‌های جزئی را می‌توان با Integration/Component Test سنجید تا E2E شکننده و کند نشود. ابزار مانند Playwright فقط پس از بررسی Stack و CI انتخاب می‌شود.

Passed، Failed، Blocked و Not Tested وضعیت‌های مجزا هستند؛ Flaky برچسب مکمل است. هر Passed باید به اجرای واقعی با Commit، Environment، Command و Artifact وصل باشد.

DEBUGGING / وقتی تست شکست می‌خورد

قبل از Fix تشخیص بده

01

Product Defect

رفتار واقعی با انتظار معتبر متفاوت است؛ در دامنه و با مجوز اصلاح شود.

02

Test Defect / Flaky

Selector، داده تست، Race Condition یا محیط مشکل دارد؛ تست را پایدار کن.

03

Spec Ambiguity

انتظار روشن نیست؛ پیش از تغییر محصول به تصمیم‌گیرنده برگرد.

04

Missing Full-stack

نیازمند Backend واقعی است؛ بدون اختیار توسعه نده، Blocker یا Backlog بساز.

ضدالگو: ضعیف‌کردن Assertion برای سبز شدن تست، ساختن Log خیالی یا برابر دانستن Mock سبز با API واقعی.
EXAMPLE / فقط آموزشی

TaskFlow: ساخت یک Task

فرض آموزشی: در منبع معتبر FLOW-01 ایجاد Task و AC-01 نمایش آن در فهرست تعریف شده باشد. Agent با داده آزمایشی Task را ایجاد می‌کند و نمایش آن را بررسی می‌کند؛ اگر شکست خورد Trace ثبت می‌شود، علت پیدا و بعد از Fix تست هدف و Smoke تکرار می‌شود.

سؤال Grill: انتظارِ ماندگاری پس از Refresh چیست؟ اگر روشن نیست، نباید خودسرانه برای این رفتار Test یا Backend ایجاد کرد. این مثال خروجی اجرای واقعی TaskFlow نیست.

EXIT / Verification Gate

شرایطی که واقعاً اجازه عبور می‌دهند

  • همه Flowهای در دامنه به منبع، AC و سناریو یا استثنای موجه وصل‌اند.
  • تست‌های ضروری بر سورس واقعی اجرا و Artifact قابل بازبینی دارند.
  • نقص‌های بحرانی رفع، تست هدف و Regression مرتبط تکرار شده‌اند.
  • Failed / Blocked / Not Tested / Flaky مالک و مسیر پیگیری دارند.
  • وابستگی Full-stack از Verified Frontend Baseline تفکیک است.
  • تصمیم صاحب اختیار با وضعیت Ready / Conditional / Blocked ثبت شده است.

Ready بودن Frontend، مجوز خودکار Backend، هزینه، استقرار یا Production نیست.
